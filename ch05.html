05Texture

模様も、その場で描く

procedural texture — UV とテクスチャ生成

この章の3行まとめ
  • 立体の表面と画像を対応づける座標を UV といいます。u が横、v が縦。
  • このプロジェクトは画像を1枚も読み込まず、1ピクセルずつ計算して描いています。
  • 描くのは色（アルベド）だけではありません。光り方と凹凸も別の画像として描きます。

立体ができたら、表面に模様を貼ります。そのために、 立体の表面のどの点が画像のどの点に対応するかを決めておきます。これが UV です。 回転体なら簡単で、u は一周した角度、v は下から上への位置にすればよい。 04章で uvs.push(j / M, t) と書いていたのがそれです。

次に画像を用意します。ふつうは写真を読み込みますが、このプロジェクトは RawTexture という「生の数値の配列」を作って、 1ピクセルずつ色を計算して詰めます。パンケーキの焼き色なら、 その位置のノイズを見て、焼けていれば茶色、焼けていなければ生地の淡い色、というふうに。

1枚では足りない。3枚要る

色の画像（アルベド）だけを貼っても、まだ紙に印刷したように見えます。 同じ焼き菓子でも、焼けていない生地はざらついて光を散らし、型に押しつけられて焼けた面は少し光る。 その差を伝えるのが2枚目の ORM です。 R に陰り（AO）、G に粗さ（Roughness）、B に金属度（Metallic）を詰めた1枚の画像で、 3つの情報を3つの色チャンネルに同居させています。

3枚目が法線マップ。細かい凹凸を、頂点を増やさずに表現します。 本当は平らなのに、法線だけを傾けて「でこぼこしている」と光に嘘をつく。 パンケーキの気泡の穴も、クッキーの型押しも、これでやっています。 クッキー.js には「型押しや格子は 0.3mm ほどしかない。頂点で出すとモアレるので、 細かい起伏は法線マップに回す」とあります。

実験 — 3枚の画像を描き分ける

左が焼いている画像そのもの、右がそれを貼った結果。 「粗さ」の画像は、白いほどざらざら（光らない）という意味です。

継ぎ目をなくす

筒に模様を巻くと、一周して戻ったところで模様がぶつかります。 03章で出てきた「u 方向に折り返すノイズ」はこのためのものです。 さらに、04章で分割の列を M+1 本にしていたのも同じ理由で、 u=0 の頂点と u=1 の頂点を別々に持たせないと、継ぎ目の面で模様が逆走します。

1cm あたりの画素の数をそろえる

ドーナツは、外周が約 22cm、穴のまわりが約 7cm です。 ここに正方形の画像を貼ると、同じ1枚の画像が外周では3倍に引き伸ばされ、 気泡が外周でだけ横に伸びます。ドーナツ.js はテクスチャを 2:1（u が長い）にして、 1cm あたりの画素の数をなるべくそろえています。 パンケーキ.js の側面も同じ考え方で、周長を約 5.8cm ごとのタイルに割り、 1枚ぶんの実寸から画像の縦横比を決めています。 画像の大きさは「何枚ぶんの細かさが要るか」ではなく、その面の実際の寸法から決めます。

つまずきポイント

法線マップの上下の符号は、環境によって逆です。 高さの画像から法線を作るとき、縦方向の差を (hd - hu) と書くか (hu - hd) と書くかで、凸が凹に化けます。 Babylon.js は V が下向きなので前者。いくつものサンプルのコメントに、 この符号を間違えて直した記録が残っています。

1mm の粒は、テクスチャでは描けません。 ドーナツのカラースプレーを色の点として描くと、遠くから見たときミップマップで溶けて 「色のにじんだ靄」になります。チョコバナナ.js やドーナツ.js が粒を1個ずつ実体として置いているのは、 それが理由です（→ 16章）。

気泡と割れ目を、暗い色で描かないでください。 ドーナツ.js とクッキー.js が同じことを書いています。割れ目の中や気泡の底は焼けていない生地なので、 むしろ周囲より明るい。暗く見えるのは窪みの陰りのぶんで、それは ORM の R（AO）と法線マップの担当です。 アルベドを暗く塗ると、カビか焦げ穴になります。

やってみよう
  1. 焼き加減を 0 から 1 まで動かし、3枚の画像がそれぞれどう変わるか見比べる。
  2. 「粗さ」だけを見て、焦げた部分と白い部分のどちらが明るいか確かめ、その理由を考える。
  3. 「立体に貼ってみる」を切り、画像だけを見たときに何の模様か分かるか試す。
  4. ドーナツ.js の doughOrm を開き、型に接した面と膨れた面で粗さがいくつからいくつまで変わるか読む。
